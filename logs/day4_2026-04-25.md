## 嘗試 1:T3A Test-Time Adaptation(失敗)

### 方法

T3A(Iwasawa & Matsuo, NeurIPS'21)— 不更新模型權重的非參數 TTA:

1. 把 `out_proj.weight` 的每一 row 視為 class prototype
2. 對 test 集走 pass1,選每 class 信心最高(entropy 最低)的 top-M=100 筆,擴充 support set
3. pass2 用「support set 平均」當新 prototype,cosine similarity × temperature 10 重新預測

實作於 `tta_t3a_pipeline.py`(已刪),套在 [outputs/siebert_oof_folds/](../outputs/folds_siebert_vanilla/) 的 5 個 checkpoint 上。

選 T3A 而非 TENT/EATA/SAR 的理由:T3A 不需要 backprop,風險低,先驗證 TTA 在這個 dataset 是否有空間。

### 結果

| 指標 | 值 |
|------|----|
| T3A vs base 預測差異 | 304 / 11000 (2.76%) |
| fp16 vs fp32 翻轉差 | 1 筆(確認 fp16 不影響結論) |
| **Kaggle Public Score** | **0.76418** |
| Delta vs siebert baseline | **-0.007** |

### 失敗解讀

T3A 假設「低 entropy 的 test 預測 = 正確」。LB 下降代表 **test 高信心預測本身就有 bias** — 模型對某類樣本(可能是長度、極性詞、Amazon vocab)有系統性高信心但實際錯誤,T3A 拿這些當 prototype 反而把分類頭拉歪。

### 對 TENT/EATA/SAR 的判斷(未實作)

三者 reliability filter 的核心都是 entropy-based。T3A 失敗的同樣機制在 TENT/EATA/SAR 上**只會更糟**:
- TENT 把錯誤信心當訓練訊號 minimize entropy,放大 bias
- EATA 的 reliability filter 同源,結構相同
- SAR 的 sharpness-aware 設計處理隨機 noise,但不處理「方向性 bias」

**結論**:整個 entropy-based TTA 家族對這個任務不適用,放棄。

## 嘗試 2:診斷腳本 `diagnose.py`(成功釐清問題)

### 方法

寫 `diagnose.py` 對 siebert OOF 做四項自動診斷:

1. **Calibration**:Reliability diagram + ECE(10 bins)+ logit-space temperature scaling
2. **OOF error confidence profile**:高信心錯比例(>0.9, >0.95)
3. **Label shift**:train P(positive) vs 各模型對 test 的預測 P(pos)
4. **Blend search**:單模 temperature scaling 後 OOF F1 變化(對 argmax F1 不變)

### 關鍵結果(siebert vanilla OOF)

| 指標 | 值 | 解讀 |
|------|----|------|
| OOF acc | 0.8710 | — |
| OOF macro-F1 | 0.8710 | — |
| **ECE (10 bins)** | **0.0872** | > 0.05,明顯失校準 |
| **Best temperature T** | **2.087** | 嚴重過度自信 |
| OOF total wrong | 258 | 12.9% 錯誤率 |
| 高信心錯 (>0.9) | 173 (67.1%) | **>30%,強烈暗示 label noise 或標註不一致** |
| 高信心錯 (>0.95) | 139 | 極端 case |

**Label shift 排除**:

| Model | pred P(pos) | shift vs train (0.5000) |
|-------|-------------|------------------------|

### 當下的(部分錯誤的)解讀

- T=2.087 + 67% 高信心錯 → **判斷為 label noise 主導**
- 推論:8.65% train 樣本疑似錯標,清乾淨後 OOF acc 上限可達 95.4%

## 嘗試 3:Adversarial Validation 分析(成功量化 covariate shift)

### 方法

在 bash 一次性 run + 後續寫成可重現腳本 `adversarial_validation.py`:

1. train(label=0)+ test(label=1)拼起來
2. TF-IDF (1-2 gram, max_features=20000) + Logistic Regression
3. 5-fold OOF 算 P(is_test) for each train sample
4. AUC 衡量分布可區分性

### 關鍵結果

| 指標 | 值 |
|------|----|
| **Adversarial Validation AUC** | **0.7468** |
| Train P(is_test) mean | 0.718 |
| Train P(is_test) std | 0.212 |
| P(is_test) > 0.7 的 train | **1317 (66%)** |
| P(is_test) < 0.3 的 train | **135 (6.7%)** |

### 分布結構解讀

train 不是「一半 SST + 一半 Amazon」,而是:
- **66% train 已經是 Amazon-style**(P(is_test) > 0.7)
- **6.7% (135 筆) 是強烈 SST/movie-only**(P(is_test) < 0.3)
- 27% 中間

### 區分性最強的詞(LR full fit)

| 偏 TEST | 偏 TRAIN |
|---------|----------|
| my, was, num_num, num_extend, am, they, game, don, these, use, doesn, used, can, coffee, it | film, movie, comedy, its, his, story, of, the film, **rrb**, films, director, documentary, **lrb**, funny, by |

**`lrb / rrb` = Penn Treebank 的 `(` / `)` token,SST 才有的標記** → 確認那 135 筆是 SST 電影評論。

### 實質意義

| AUC 範圍 | 解讀 |
|---------|------|
| ~0.5 | 分布相同,IW/filter 沒空間 |
| 0.6–0.8 | **0.7468 落在這裡** — 中度 shift,IW/filter 有效 |
| > 0.8 | 強 shift,必做 |

→ filter 那 135 筆有理論支持,期望 LB +0.001~+0.005。

## 嘗試 4:GCE + Label Smoothing 的 robust pipeline(數學 bug + 失敗)

### 動機

Diagnose 結果暗示 label noise 主導,**選擇 GCE(q=0.7) + LS(eps=0.1)組合**處理過度自信:
- LS:把 hard label `[1,0]` 改成 `[0.9,0.1]` → 抑制 train 過度自信
- GCE:對低 p_y 樣本梯度衰減 → 噪聲樣本不壓垮訓練

寫於 `siebert_oof_robust_pipeline.py`,override `Trainer.compute_loss` 用自製 loss:

```python
soft_target = (1 - ls) * onehot + ls / num_classes
per_class = (1 - probs.pow(q)) / q
loss = (soft_target * per_class).sum(-1).mean()
```

### 第一次跑的結果(看似 OK,實則糟)

| 指標 | vanilla | robust v1 (GCE+LS) |
|------|---------|---------------------|
| OOF F1 | 0.8710 | 0.8720 |
| **ECE** | **0.0872** | **0.1205** ← 變糟 |
| **T** | **2.087** | **3.025** ← 更過度自信 |
| 高信心錯 (>0.9) | 173 (67.1%) | **245 (95.7%)** ← 嚴重變糟 |
| `[0.9,1.0]` bin 樣本數 | 827 | 983 ← 預測更極端 |

**結果反向了** — 預測比 vanilla 更極端。

### 數學 bug 分析

我用「soft target × per-class GCE」這樣相乘:

$$L = \sum_c t_c \cdot \frac{1 - p_c^q}{q}$$

求極值(constraint $\sum p_c = 1$,Lagrangian):

$$p_c^{q-1} = \lambda / t_c \Rightarrow p_c \propto t_c^{1/(1-q)}$$

對 $t = [0.95, 0.05]$、$q = 0.7$:

$$p_c \propto t_c^{1/0.3} = t_c^{3.33}$$

$$p_0 \propto 0.95^{3.33} \approx 0.836,\quad p_1 \propto 0.05^{3.33} \approx 7.6 \times 10^{-5}$$

正規化後 **$p \approx [0.99991, 0.00009]$ — 比 LS 沒做還更極端**!

**根本原因**:CE 有「soft target → soft prediction」的性質(因 log 函式),GCE 沒有。它們不能用「target 加權 per-class loss」這樣的方式組合,會反向放大自信度。

### 修正:改用純 LS-only(HF 內建 `label_smoothing_factor=0.1`)

移除自製 `RobustTrainer`,改用 `TrainingArguments(label_smoothing_factor=0.1)`,標準 LS-CE。

### 第二次跑的結果(LS-only)

| 指標 | vanilla | robust v2 (LS-only) | Delta |
|------|---------|---------------------|-------|
| OOF F1 | 0.8710 | 0.8720 | +0.0010 |
| **ECE** | **0.0872** | **0.0560** | **-0.0312** ✓ |
| **T** | **2.087** | **1.284** | **-0.803** ✓ |
| 高信心錯 (>0.9) | 173 (67.1%) | 156 (60.9%) | -17 |
| **超高信心錯 (>0.95)** | **139** | **32** | **-107 (降 77%)** |

**校準指標全面改善**,T 從 2.087 拉回近 1。

### Kaggle Public Score(關鍵反證)

## 反思:67% 高信心錯不是 label noise,是 hard cases

### 反證邏輯

LS 把超高信心錯從 139 砍到 32(-77%),如果這 139 筆是 label noise:
- LS 把它們從「錯標」搶救回「正確」
- test 上類似樣本也跟著正確
- **LB 應上升**

實際 **LB 下降 0.005**。所以那 139 筆**不是 label noise,是 hard cases**:
- train label 標的方向跟模型「自然信念」相反
- 因為它們是反諷 / 委婉 / 混合極性等真正困難的語言現象
- LS 強迫模型不要太確定 → test 上類似困難樣本被推向錯誤方向

### 跟 Day 3 divergence_report 的對應

[outputs/divergence_report.txt](../outputs/report_divergence.txt) 早就標記出最高分歧的 20 筆 test 樣本:

- "**nothing sticks to it**"(不沾鍋讚美)
- "**thank goodness for consumers who pay attention to reviews before buying such rubbish**"(罵產品但用 thank goodness)
- "**this case was too good to be true**"(反諷)
- "**they are not made for this, they are storage caps and they are wonderful when used as storage caps**"(否定+重定位後肯定)
- "**the stuff lasts what seems like forever, it didn't stop burning for hours**"(反諷)
- "**this bra feels good for about the first num_num hours you wear it**"(限定條件型負評)

OOF 高信心錯的可能就是**同一批反諷/混合句**,不是錯標。

### 我自己的判斷錯誤

Day 4 中段我看到 67% 高信心錯就推論為 label noise → LS。應該更早把這個數字跟 [outputs/divergence_report.txt](../outputs/report_divergence.txt) 的反諷/concession 樣本清單對上號,就會發現「高信心錯」很可能是「genuinely hard」而非「genuinely mislabeled」。

**教訓**:單一統計指標(67% 高信心錯)有多種可能解釋,在沒有對照(LB 結果)前不該選定其中一個方向投資。

## 觀念整理:OOF (Out-Of-Fold) 預測 — 給總結報告用

### 定義

K-fold cross-validation 中,**每一筆 train 樣本都被「沒看過它的模型」預測一次**,把 K 個 fold 的 val 預測拼接回來 → 全 train 集的 OOF 預測。

```
fold 0: train [400~2000] → predict val [0~400]
fold 1: train [0~400, 800~2000] → predict val [400~800]
...
fold 4: train [0~1600] → predict val [1600~2000]

OOF[0:400]   ← fold 0 model 的預測
OOF[400:800] ← fold 1 model 的預測
...
```

關鍵性質:**沒有任何模型預測它自己訓練過的樣本**。

### 為什麼必須用 OOF(不能用 train predictions)

1. **誠實的 CV 估計**:train predictions 會 overfit — 模型對自己訓練過的資料記憶痕跡仍在,F1 會虛高(本資料集上 train acc 通常 0.99+,但 OOF F1 是 0.871)
2. **Stacking / blend 唯一合法的訓練材料**:若 meta-learner 的輸入特徵是「模型自己對 train 的預測」,等於模型答自己看過的考題,**完全 leakage**,meta 會學到一個假的訊號,在 test 上崩盤
3. **Calibration 必須用無偏 holdout**:Temperature scaling / ECE 計算需要「模型沒看過的」預測,train predictions 會給出失真的校準參數
4. **Adversarial validation 跟 model diversity 比較也需要 OOF**:要算「兩模型在 train 上的一致率」,雙方都必須是 OOF,不然一致率會虛高(都是各自 overfit 的版本對照)

### 報告中的關鍵句

如果要在報告或答辯中提這點:

> "我們對所有需要 ensemble 或 stacking 的模型都產出 5-fold Out-Of-Fold (OOF) 預測,而不是 train-set predictions。OOF 確保每筆 train 樣本的預測都來自一個沒看過它的模型,因此可以提供無偏的泛化估計、合法的 stacking 訓練材料,以及無偏的校準參數估計。如果用 train predictions 直接做 stacking,meta-learner 會學到一個 leakage 訊號,在 test 上失效。"

### 何時 OOF 不必要

- 純粹要產出 submission 而不打算 blend / stack / 校準 → 5-fold 平均 test 機率即可
- Day 1 baseline、Day 2 pseudo-labeling 就是這種情況,沒有存 OOF
- 但只要打算「將來可能 ensemble」,**第一次跑就該存 OOF**,否則重訓成本比直接保留 OOF 高 5 倍

### 跟「跑多次模型」的取捨

| 目的 | 該怎麼跑 | 成本 |
|---|---|---|
| 只要單模 submission | 1 次 train(全 2000 筆 → predict test)| 1× |
| 想評估泛化(報告用 CV)| 5-fold CV(可不存 OOF)| 5× |
| **想 ensemble blend / stacking** | **5-fold OOF(必須跟其他模型同 split)** | **5×** |
| 想多 backbone diversity 但 GPU 緊 | 3-fold OOF(噪聲略多但可用)| 3× |

關鍵:**OOF 只有當所有模型用同一個 fold split 時才能拼成有效的 stacking 材料**。換 seed 或 split,OOF 就對不上。本專案所有 OOF pipeline 都鎖 seed=42, n_splits=5, shuffle=True 對齊。

## 嘗試 5(中段插入):ELECTRA-large collapse 事件 + 回溯 Day 2 DeBERTa 失敗根因

### 事件經過

下午改路線轉做 ensemble diversity:寫 [electra_oof_pipeline.py](../pipe_electra_vanilla.py),選 `google/electra-large-discriminator`(335M params,跟 siebert 容量接近,但預訓練目標 RTD 跟 RoBERTa MLM 不同)當第二成員。

跑到第 2 fold:

```
Fold 1 Val F1 = 0.8750     ← 正常
Fold 2 Val F1 = 0.3333     ← 完全 collapse, 模型只預測一個 class
```

**Macro-F1 = 0.3333 在二元 50/50 平衡資料上 = 模型輸出全部同一類**。不是普通的訓練不夠,是**收斂到 degenerate 解**。

### 根因:transformer-large 在小資料 FT 的 instability

**Mosbach et al. (ICLR 2021)** *"On the Stability of Fine-tuning BERT"* 已系統研究:
- BERT/ELECTRA/DeBERTa-large 在 < 5000 筆 FT 時,**約 20-30% 隨機 seed 會 collapse**
- 跟模型容量 / 隨機 init 的 classifier head / Adam bias correction 互動有關
- 跟資料品質、標籤、loss 都無關 — **就是 seed 運氣**

3 個共同觸發因素:
1. **Classifier head 隨機初始化**:某些 seed 的 init 在「梯度給不出方向」的死角
2. **Warmup 太短 + lr 太大**:前期梯度大,在死角附近震盪卡死
3. **Early stopping patience=1 + epochs=3**:bad-init 的 fold 沒時間復活就被砍掉

### 修法(寫進 [electra_oof_pipeline.py](../pipe_electra_vanilla.py))

| 參數 | 舊 | 新 | 來源 |
|---|---|---|---|
| `FT_EPOCHS` | 3 | **5** | 給 bad-init 復活時間 |
| `FT_LR` | 1e-5 | **5e-6** | Mosbach 2021 建議 |
| `warmup_ratio` | 0.1 | **0.2** | 同上 |
| `early_stopping_patience` | 1 | **2** | 不要太早放棄 |
| `adam_epsilon` | 1e-8(預設)| **1e-6** | 抑制 bias correction collapse(Mosbach 2021 重點) |
| **+ collapse retry 安全網** | 無 | F1 < 0.6 自動換 seed 重訓 ≤ 2 次 | 自加 |

### 回溯:Day 2 DeBERTa-v3-large 是同一個 bug

對照 [logs/day2_2026-04-23.md](day2_2026-04-23.md) 的 DeBERTa 記錄:

| 版本 | Day 2 觀察 | Day 4 重新解讀 |
|------|-----------|----------------|
| bf16 + lr=5e-6 | `Attempting to unscale FP16 gradients` 錯誤 | precision 問題,獨立議題 |
| bf16 + lr=1e-5 | train loss 1.5→1.42, **val F1 = 0.3333 (全預測同一類)** | **跟今天 ELECTRA Fold 2 完全相同症狀** |
| bf16 + lr=1e-5 + 手動 init classifier/pooler | loss 0.7→1.1→0.69 震盪, **val F1 = 0.3333** | 手動 init 是對的方向,但缺其他 4 個修法(小 lr / 長 warmup / 大 adam_eps / 多 epoch) |

Day 2 結論「DeBERTa-v3-large 在此環境不可用」**錯把症狀歸因到環境**:
- 真實原因:**transformer-large + 小資料(2000 筆)+ Mosbach 描述的 5 個觸發因素同時存在**
- 環境的 mixed precision 問題只是其中一個觸發
- DeBERTa-v3 的 disentangled attention 對 fp16 梯度確實更敏感 → 但**就算把 fp16 換成 fp32 也救不了 collapse**,因為核心問題不在精度

### 教訓

1. **F1 = 0.3333(二元平衡)= class collapse,不是泛化失敗**:看到這個數字直接套 Mosbach 修法,別 debug 模型架構或環境
2. **Day 2 當下若認得這個訊號,DeBERTa 應該救得回來** — 但 Day 2 的方向(換 lr / 換精度 / 換 init)是逐項試,沒系統 — Day 4 的 5 個修法應該一次全上才對
3. **任何 large 模型 + 小資料 FT,預設配 collapse retry 安全網**:GPU 比工程師時間便宜

## 嘗試 5(continued):Adversarial Validation Filter pipeline(失敗)

### 動機

T3A 失敗 + LS 失敗後,訓練端唯一還沒試的槓桿。AUC=0.7468 確認 covariate shift 中度存在,135 筆 SST 樣本是污染,理論上 drop 後訓練訊號更純粹,test 預測應該變好。

寫於 [siebert_oof_filtered_pipeline.py](../pipe_siebert_advfilter.py),**唯一改動**是訓練前依 `outputs/adv_val_keep_indices.npy` 過濾 train(2000 → 1865),其他超參、loss、optimizer 全部跟 vanilla [siebert_oof_pipeline.py](../pipe_siebert_vanilla.py) 一致。**故意不疊 LS**,單獨驗證 filter 的效果。

### 結果

| 指標 | vanilla | filtered | Delta |
|------|---------|----------|-------|
| CV F1 | 0.8710 ± 0.0052 | 0.8579 ± 0.0230 | CV 不直接可比(val set 不同) |
| std | 0.0052 | 0.0230 | std 跳 4.5× |
| **Kaggle Public Score** | **0.77107** | **0.76501** | **-0.006** |

**LB 又降了**。

### 反證解讀

理論上 drop 跟 test 不像的樣本應該幫助 test 預測。LB 下降代表:

1. **6.7% 樣本量損失壓過收益**:1865 筆比 2000 筆少 6.7%,large 模型在這個 sample size 下開始 underfitting
2. **OR 那 135 筆雖然詞彙偏 SST,但對訓練有「正則化」價值**:multi-domain 訓練給模型更廣的語境覆蓋,純 Amazon-style 訓練反而過擬合到某種狹窄 pattern
3. **OR 跟 LS 失敗同樣機制**:filter 後模型對「跟 SST 像」的 test 樣本更不確定,而 test 裡可能仍有少量這種樣本

std 從 0.005 跳到 0.023(4.5×)是 underfitting 訊號:
- val set 變難 + train 變少 → fold 之間訊號不穩
- 不是 5×5=25 fold 變化,只是 5 fold 平均更不穩

### 結論

**訓練端基本到頂**。繼續砸 GPU 在「動 train 資料 / 動 loss」這條路徑期望值已經是負的:T3A、LS、Filter 三連敗,三個機制完全不同(inference-time / training-time soft target / training-time data filter)都失敗,代表 0.77107 不是某個技術沒做對的問題,而是 siebert + 5-fold + 全 train 在這個 LB 上的結構性上限。

## 嘗試 7:Multi-seed siebert ensemble(訓練完成,LB 待 Day 5 提交)

### 動機

ELECTRA blend 失敗後,訓練端 + diversity 兩條路都試完。最後一個還沒試的槓桿是**純 variance reduction**:用同一個 backbone(siebert)跑 3 個獨立 seed × 5 fold = 15 trainings,平均後得到比 single-seed 更穩定的預測。

理論上界(Kaggle 經驗法則):multi-seed 比 10-fold 期望增益更大,因為多 seed 提供 3 個獨立隨機性來源的乘積:
1. 不同 KFold split(`random_state=seed` 變化 → val 集不同)
2. 不同模型 init(classifier head 從 scratch 受 set_seed 影響)
3. 不同 DataLoader shuffle 順序(受 data_seed 影響)

而 10-fold 的 fold 之間共享 90% 資料,模型相關性高,平均效益快速飽和。

### 實作:[siebert_multiseed_pipeline.py](../pipe_siebert_multiseed.py)

從零重寫(不參考 [siebert_oof_pipeline.py](../pipe_siebert_vanilla.py)),寫完比對:

| 項目 | siebert_oof | multiseed | 評估 |
|---|---|---|---|
| BASE_MODEL / lr / batch / epochs / warmup | 一致 | 一致 | ✓ |
| `ignore_mismatched_sizes=True` | ✓ | 漏寫已補 | ✓ |
| `__main__` 頂層 seed | ✓ | 漏寫已補 | ✓ |
| `adam_epsilon` | 預設 1e-8 | **1e-6**(Mosbach)| 故意改善 |
| `early_stopping_patience` | 1 | **2**(Mosbach)| 故意改善 |
| Pre-tokenize 一次後 index 切片 | per-fold tokenize | once | 故意改善(省時) |
| Checkpoint 清理 | del trainer/model | del + shutil.rmtree | 故意改善(15 fold × 2GB 不清會塞爆) |
| Collapse retry(F1<0.6 換 seed) | 無 | ✓ | 故意改善 |
| Multi-seed 外層 loop | — | ✓ | 主要新功能 |

→ 重寫後沒發現 silent bug,只發現 2 個漏寫(已補)+ 多個故意的改善。

### 訓練結果

```
Seed   42: CV F1 0.8670 ± 0.0125  |  OOF 0.8670
Seed  123: CV F1 0.8649 ± 0.0076  |  OOF 0.8650
Seed 2024: CV F1 0.8680 ± 0.0078  |  OOF 0.8680
─────────────────────────────────────────────
Averaged OOF F1   = 0.8690
Pred distribution : neg=990  pos=1010
Single-seed siebert vanilla baseline OOF F1 = 0.8710 (參考)
```

### 解讀:OOF -0.002 vs vanilla 是統計噪聲,不是 bug

**為什麼新 pipeline seed=42 是 0.8670 而非 vanilla 的 0.8710**:

| 參數 | siebert_oof | multiseed |
|---|---|---|
| trainer seed (per fold) | `42 + fold_idx` (42, 43...46) | `seed*100 + fold_idx` (4200, 4201...4204) |
| `adam_epsilon` | 1e-8 | 1e-6 |
| `early_stopping_patience` | 1 | 2 |

「seed=42」這個標籤不完全鎖住結果 — 不同 trainer seed 給不同 model init / batch order;Mosbach 安全網改變優化軌跡。**0.004 差距落在 CV std 範圍(0.008~0.013)內**,是統計噪聲。

**重點:Average (0.8690) 比 3 個單 seed (0.866 平均) 高 0.003 — variance reduction 確實生效**。基準下移 + 平均後上移,代表 multi-seed 的數學是對的,只是起點略低於 vanilla single-seed。

## 反思:Day 4 的方法論失誤

### 錯誤判斷的時間軸

1. T3A 跑完 LB 0.764 → **正確**判斷 entropy-based TTA 不適用
2. 看 67% 高信心錯 → **錯誤**判斷為 label noise(忽略 hard cases 解釋)
3. 寫 GCE+LS 組合 loss → **數學 bug**(沒驗證最佳解形式)
4. 修成 LS-only,ECE 從 0.087 降到 0.056 → **過度樂觀**,以為 LB 也會跟著上
5. LB 反而降 0.005 → **才反推**是 hard cases

### 應該怎麼避免

- 在投資 GPU 重訓之前,**先做小規模 sanity check**:把 siebert 在 train 高信心錯的 173 筆抽 20 筆人眼看,如果**多數看起來標籤合理但語境困難** → 那不是 label noise,LS 不會幫忙
- 任何自製 loss **先在玩具資料集驗證最佳解形式**,不要直接放上 5-fold × roberta-large
- **「校準改善」≠「LB 改善」**:LB 是 argmax 後的 0/1,校準改的是機率分布,兩者只有間接關係
